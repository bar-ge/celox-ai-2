## 1. מטרה

להבטיח שימוש נכון ואפקטיבי בהצפנה להגנה על הסודיות, האותנטיות והשלמות של מידע Celox AI.

## 2. תקני הצפנה

### 2.1 מידע במעבר
| חיבור | פרוטוקול | תקן מינימום |
|-------|----------|-------------|
| דפדפן משתמש ↔ אפליקציית Celox AI | HTTPS | TLS 1.2 (עדיף TLS 1.3) |
| אפליקציה ↔ API של Supabase | HTTPS | TLS 1.2+ |
| מכשיר GPS ↔ פונקציית קליטת GPS | HTTPS | TLS 1.2+ |
| כל שאר חיבורי ה-API | HTTPS | TLS 1.2+ |

חיבורי HTTP מנותבים אוטומטית ל-HTTPS. Vercel ו-Cloudflare אוכפים סיום HTTPS.

### 2.2 מידע במנוחה
| סוג מידע | תקן הצפנה | היכן |
|----------|-----------|------|
| מסד נתונים (כל הטבלאות) | AES-256 | Supabase (הצפנת AWS RDS) |
| אישורי API של אינטגרציות | AES-256 דרך pgcrypto | RPC בשם `store_integration_credential()` |
| גיבויים | AES-256 | הצפנת גיבוי Supabase |
| מחשב נייד / דיסק מפתח | AES-128 או AES-256 (BitLocker/FileVault) | תחנת עבודה מקומית |

### 2.3 גיבוב סיסמאות
- סיסמאות משתמש מגובבות באמצעות **bcrypt** (cost factor ≥ 10) בניהול Supabase Auth
- סיסמאות לעולם אינן נשמרות כטקסט גלוי
- hash-ים של סיסמאות לעולם אינם נרשמים בלוג או משודרים

### 2.4 אסימוני JWT
- אסימוני סשן משתמשים ב-**RS256** (RSA + SHA-256) בניהול Supabase Auth
- תפוגת אסימון: 8 שעות (בהתאם לפסק-זמן הסשן)
- אסימוני refresh הם חד-פעמיים ומוחלפים בכל שימוש

## 3. ניהול מפתחות

### 3.1 סוגי מפתחות ואחסון

| סוג מפתח | מיקום אחסון | גישה |
|----------|-------------|------|
| מפתח anon של Supabase | משתני סביבה ב-Vercel | Frontend (בטוח — RLS נאכף) |
| מפתח service role של Supabase | משתני סביבה ב-Vercel (צד שרת בלבד) | Backend בלבד |
| מפתחות הצפנת מסד נתונים | בניהול Supabase/AWS KMS | רמת תשתית |
| מפתח הצפנת pgcrypto לאינטגרציות | Supabase Vault / משתנה סביבה | פונקציות RPC בלבד |
| סוד Cloudflare Turnstile | משתני סביבה ב-Vercel (צד שרת) | Backend בלבד |

### 3.2 החלפת מפתחות
| מפתח | תדירות החלפה | טריגר להחלפה מיידית |
|------|---------------|---------------------|
| סוד JWT של Supabase | שנתית | חשד לפריצה |
| מפתח הצפנת אינטגרציות | שנתית | חשד לפריצה |
| אסימוני webhook (לכל חברה) | בשליטת הלקוח | לפי בקשה או אירוע |
| סודות OAuth client | שנתית | חשד לפריצה |

### 3.3 תגובה לפריצת מפתח
אם קיים חשד שמפתח נפרץ:
1. להחליף מיידית — לא להמתין לאישור
2. לתעד כאירוע אבטחה P1/P2
3. לבקר את כל הגישה האחרונה במפתח שנפרץ
4. להודיע לצדדים מושפעים אם התרחשה חשיפת מידע

### 3.4 נהלים אסורים
- אין להכניס סודות לקוד המקור (סריקת סודות של GitHub מופעלת)
- אין לאחסן מפתחות בקוד צד-לקוח או באחסון דפדפן
- אין לשדר מפתחות באימייל או הודעות
- אין להשתמש באלגוריתמים מיושנים (MD5, SHA-1, DES, RC4)
- אין להשתמש בתעודות self-signed לייצור

## 4. ניהול תעודות

| תעודה | ספק | חידוש |
|-------|-----|-------|
| תעודת TLS של celoxai.com | Cloudflare / Let's Encrypt (אוטומטי) | אוטומטי |
| TLS של פרויקט Supabase | Supabase (מנוהל) | אוטומטי |
| TLS של פריסת Vercel | Vercel (מנוהל) | אוטומטי |

כל התעודות משתמשות ב-RSA-2048 או ECDSA P-256 כמינימום.
