## 1. תמצית מנהלים

בוצע מבחן חדירה ממוקד בשכבת האפליקציה מול פלטפורמת Celox AI, בדגש על משטח התקיפה של SaaS רב-דיירי: אימות, בידוד דיירים (RLS), edge functions, אחסון, וטפסים ציבוריים.

**תוצאה:** זוהו **3 ממצאים קריטיים, 2 גבוהים, ומספר בינוניים/נמוכים** — כולם **תוקנו ואומתו במהלך הבדיקה**. החמור ביותר היה נתיב הסלמת-הרשאות חוצה-דיירים שאיפשר לכל משתמש רשום להפוך למנהל של חברה אחרת. כל הממצאים הקריטיים והגבוהים סגורים כעת.

|-------|-------|-------|--------|
| קריטי | 3 | 3 | 0 |
| גבוה | 2 | 2 | 0 |

## 2. מתודולוגיה

- **תקן:** OWASP Top 10 (2021) + OWASP ASVS, בתוספת בדיקות RLS/בידוד-דיירים ייחודיות ל-Supabase.
- **גישה:** סקירת מדיניות RLS ופונקציות `SECURITY DEFINER` חיות מול קוד המקור; בדיקת זרימות אימות, edge functions, גישה לאחסון, וטפסים ציבוריים; מעקב זרימת מידע מקלט לא-מהימן ועד פעולה רגישה.
- **מוקדי מיקוד:** בידוד רב-דיירי, אימות/סשן, IDOR/BOLA, הזרקות, חשיפת סודות, לוגיקה עסקית.

## 3. ממצאים

### PT-01 — השתלטות חוצת-דיירים דרך הכנסה עצמית ל-`profiles` — **קריטי** — תוקן
מדיניות ה-RLS `profiles_insert` בדקה רק `id = auth.uid()`, לא `company_id`/`role`, ולא היה טריגר ליצירת פרופיל. כל משתמש רשום יכול היה להכניס פרופיל עם `company_id` שרירותי ו-`role='admin'`, ולקבל גישת מנהל מלאה לכל הצי של חברה אחרת.
- **השפעה:** דליפת מידע ושליטה חוצת-דיירים מלאה.
- **תיקון:** ההצטרפות הועברה ל-RPCs מסוג `SECURITY DEFINER` (`join_company_by_code`, `accept_company_invite`); `profiles_insert` הוקשח כך שהכנסה עצמית דורשת `company_id IS NULL` ותפקיד לא-מורשה. אומת חסום.

### PT-02 — ממסר אימייל פתוח לא-מאומת (`send-report`) — **קריטי** — תוקן
לפונקציית `send-report` לא היה אימות, והיא קיבלה נמענים, נושא ו-HTML שרירותיים, ושלחה מהדומיין המאומת `celoxai.com`.
- **השפעה:** כלי פישינג/ספאם מהדומיין המותגי; פגיעה במוניטין.
- **תיקון:** הפונקציה דורשת כעת משתמש מאומת עם חברה (אימות JWT); מספר הנמענים מוגבל. אומת.

### PT-03 — טבלת `form_links` קריאה לכולם — **קריטי** — תוקן
מדיניות RLS מתירנית (`is_active = true`) איפשרה לתפקיד `anon` הציבורי לקרוא את כל קישורי הטפסים הפעילים של כל דייר — אסימונים, מזהי חברה, ותמחור מסחרי בקישורי הסכם רישיון.
- **השפעה:** דליפת אסימוני יכולת ומידע עסקי חוצת-דיירים.
- **תיקון:** מדיניות הקריאה הציבורית הוסרה; האפליקציה קוראת קישור בודד דרך ה-RPC `get_active_form_link(token)`. אומת שהוסר.

### PT-04 — הזרקת HTML + פישינג בחירת-נמען (`send-notification`) — **גבוה** — תוקן
שדות ה-payload שולבו במיילים ללא escaping, ונתיב `invite_sent` איפשר לקורא לא-מאומת לבחור נמען.
- **תיקון:** כל השדות עוברים escaping; `invite_sent` דורש אימות מנהל-של-החברה ושואב את זהות המזמין מה-JWT. אומת.

### PT-05 — CAPTCHA בטופס יצירת קשר לא מאומת בשרת — **גבוה** — תוקן
וידג'ט Turnstile הוצג בצד לקוח אך מעולם לא אומת בשרת; `crm_leads` קיבלה הכנסות אנונימיות בלתי-מוגבלות.
- **תיקון:** פונקציית `contact-form` מאמתת כעת Turnstile מול Cloudflare siteverify ומכניסה דרך service role; מדיניות `anon_insert_leads` הוסרה. אכיפה אומתה (אסימון לא תקין → 403).

### PT-06 — אובדן שקט של העלאת קבצים בטפסים ציבוריים — **בינוני** — תוקן
העלאות אחסון שנכשלו נשמטו בשקט בעוד הטופס דיווח הצלחה — סיכון לאובדן ראיות בדוח תאונה.
- **תיקון:** ההעלאות זורקות שגיאה בכשל וכל טופס מציג את השגיאה.

### PT-07 — `search_path` משתנה בפונקציות אישורים — **בינוני** — תוקן
פונקציות `SECURITY DEFINER` לניהול אישורי אינטגרציה (save/delete/get) לא קיבעו `search_path` — וקטור הסלמת-הרשאות.
- **תיקון:** `SET search_path = public` קובע בשלושתן; הרשאת EXECUTE ל-anon בוטלה ב-RPCs של ההצטרפות.

### PT-08 — לוג ביקורת אימות מת — **בינוני** — תוקן
`log_auth_event` נקרא עם `.catch()` על builder שרץ רק בהמתנה, כך שאירועי כניסה/יציאה מעולם לא נרשמו (פער לוגים ב-ISMS).
- **תיקון:** תוקן ל-`.then(null, noop)`; אירועים נרשמים כעת.

### PT-09 — אסימוני סשן במובייל ב-AsyncStorage — **נמוך** — מקובל (backlog הקשחה)
אפליקציית המובייל שומרת אסימוני סשן ב-AsyncStorage לא-מוצפן. ניתן לניצול רק בגישה פיזית/מכשיר פרוץ. מומלץ `expo-secure-store`. נרשם ל-build מובייל עתידי.

### PT-10 — דליפת שגיאות לא-מתורגמות / קוסמטי — **נמוך** — תוקן
שגיאות Supabase באנגלית הוצגו בממשק העברי; תוקן עם מיפוי מתורגם.

## 4. חוזקות שנצפו

- כותרות האבטחה ב-`vercel.json` חזקות: CSP קפדני (ללא `unsafe-inline`/`unsafe-eval`), HSTS preload, `X-Frame-Options: DENY`, `nosniff`, `Permissions-Policy` ממוקד.
- ה-bucket פרטי עם signed URLs קצרי-מועד; שמות קבצים מנוקים.
- פונקציות `trigger-alerts` ו-`gps-ingest` מאמתות כראוי.
- CAPTCHA בכניסה/הרשמה מאומת כראוי ע"י Supabase Auth.
- אישורי אינטגרציה מוצפנים במנוחה דרך pgcrypto.

## 5. המלצות ותדירות

1. לסגור את PT-09 (אחסון מאובטח במובייל) ב-build המובייל הבא.
2. להפעיל "הגנה מפני סיסמאות שדלפו" ב-Supabase Auth (HaveIBeenPwned).
3. לחזור על הבדיקה כל **12–18 חודשים** ואחרי שינוי גדול (תואם לציפיית מבחן החדירה התקופתי בתקנות אבטחת המידע למאגרים ברמה גבוהה — ראו `docs/compliance/amendment-13/`).
4. לשקול **פנטסטר חיצוני מוסמך** לדוח אמין למבקר לקראת שלב 2 של ISO 27001.
